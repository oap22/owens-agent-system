# Development

1. Inspect repository instructions, git state, worktrees, and active ownership. Use an isolated task worktree and preserve unrelated changes.
2. Define observable before/after behavior. For substantial changes, record acceptance criteria, design decisions, risks, and validation before implementation; scale the record to the change. Use `plan-then-ship` when appropriate.
3. When delegation is authorized, give an independent slice to `implementor` only if its check is executable and its reading would otherwise crowd the lead's context. Use `templates/task-packet.md` for owned paths, entry points, acceptance criteria, budget, and report. Keep coupled edits or intent questions in the lead. Workers must know they share the codebase.
4. A worker that exhausts its budget returns partial work and evidence. Diagnose the failure before retrying: missing access, bad inputs, and a broken check need correction, not more effort. For a reasoning or implementation failure, use `implementor-retry` once if configured; otherwise take the slice in the lead. Count every attempt with `oas.py log-run` when evaluating the split.
5. Implement every requested behavior. Add focused regressions for bugs and meaningful failure boundaries, sized like neighboring tests. Use scratch checks for reversible low-impact changes. Run the relevant checks after a coherent change; repeat or broaden them only after new edits, failures, or an unresolved concern.
6. Review the diff and requirement coverage. Use `adversarial-review` when applicable and authorized; otherwise label self-review. Reuse passing evidence for unchanged code. Validate native behavior for platform-sensitive changes. Stop verification when the criteria and required checks are satisfied.
7. Commit reviewed files. Push and merge within the user's authorization after required CI and review gates. Distinguish local checks, hosted CI, merge, installation, and deployment.
8. Checkpoint after planning, completed implementation slices, and before release or compaction. Record commit, worktree, ownership, completed criteria, evidence paths, failing checks, risks, and next action. After compaction or resume, reload the checkpoint and verify the current git state and affected checks before acting.

Skill routing: `plan-then-ship`, `adversarial-review`, `publish-to-github`, `project-sync`; `turing` for that repository. Read selected skill instructions at use time.
