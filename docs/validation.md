# Validation scope

The unit suite covers configuration merging and safety defaults, shell-safe argument construction, workspace validation, prompt composition, task traversal and overwrite protection, completion evidence, and export behavior. It uses disposable fixtures and no model calls.

`check` validates all source TOML files, required workflow files, role paths, scenario IDs, and that the `implementor` role is registered with instructions that render as valid Claude Code `--agents` JSON. The unit suite also covers the lead-effort and worker-option mapping for Codex and Claude, the generated Codex role layer, explicit Claude auto-compaction, OpenCode setup merging, version-2 continuity checkpoints with version-1 compatibility, and refusal on adapters and modes that do not support delegation. It does not run a paid model turn, so native compaction trigger timing and summary quality remain to be confirmed with recorded evaluations. It also compares the skill names routed in `workflows/*.md` against `~/Developer/active/skills/skills` (override with `--skills-root PATH`); a routed name with no matching directory is reported as an advisory warning on stderr and `check` still exits 0. When that directory is absent the routing check is skipped and says so. `doctor MODE` asks the installed Codex to parse the exact merged overrides with strict config enabled. That is not proof the interactive client accepts them: on 2026-09-07 `doctor` passed a profile whose `apps._default.default_tools_enabled` key the TUI rejects at startup as an unknown field. After changing a Codex override, start the client once with `oas run` or the launcher and confirm no `Error loading config.toml` line appears. It can also report unrelated inherited hook, plugin, authentication, or connector problems. Inspect the actual check categories before attributing a warning to this kit.

`tests/test_oas_ui.py` exercises the interactive launcher's state machine (`scripts/oas_ui.py`): screen transitions, cursor movement and disabled-row skipping, the directory browser's descend/up/choose/cancel behavior, task-field editing and the empty-task and `ValueError` paths, return-to-home preselection and `last_exit`, and the rain geometry and key mapping in `scripts/oas_screen.py` (cell bounds, faint mode, `keyname` translation). It also checks the no-terminal refusal when stdin or stdout is not a TTY. None of it renders a real terminal: no test calls `curses.wrapper` or `initscr`, so panel layout, logo placement, color pairs, and the `--plain`/`NO_COLOR` rain-disable path inside `run_ui`'s session loop are not exercised; only the pure pieces (`Rain`, `logo_lines`, `keyname`, and `run_ui`'s pre-terminal TTY check) are.

Initial runtime and publication results are recorded in `docs/build-report.md`. Native desktop adoption, live mail/calendar/Linear/ROSIE actions, and comparative model-quality evaluations require separate evidence. No claim of optimal performance follows from CI.
